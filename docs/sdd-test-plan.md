# SDD Test Plan

Manual scenario catalog to test the effectiveness of every flow in the `sdd` domain. "Effectiveness" here means: the `orchestraitor` and its subagents honor the contracts written in `domains/sdd/agents/*.md`, the `sdd-draft-*` and `judgment-day` skills, and `docs/plan-handoff.md` — observable artifacts, gates, receipts, and exact strings — when run in a real OpenCode session.

Companion mechanisms: `scripts/validate-harness.sh` covers static structure only (frontmatter, symlinks, SemVer); nothing else exercises flow behavior today. The known contradictions found by the 2026-07-29 flow review (`.ai/absorb/2026-07-29-sdd-flow-review.md`) appear here as **negative tests** expected to FAIL until fixed.

## How to judge results

Judge every scenario by **observable evidence only**, never by what the agent claims in chat:

- Files written (paths, first lines, exact strings).
- Gate questions asked — or, just as important, *not* asked.
- Receipt terminal tokens (`VERIFY: ALL PASS — <n>/<n> scenarios.`, `FIX: <n> fixed, <m> open.`, `VERDICT: CLEAN — No issues found.`, `JUDGMENT: …`).
- `git log` / `git status` for delivery scenarios.
- Which subagents were (not) launched, visible in the session's task activity.

LLM behavior is nondeterministic: run each P0 scenario at least twice before recording a FAIL, and note the model profile used (see `docs/agent-models.md`). A scenario passes only when every listed pass criterion holds.

## Test environment

1. Create a scratch project: `git init` a throwaway repo with a small real codebase (a few source files plus a runnable test command) — flows like implement/verify need something to build against.
2. Install the harness into a scratch OpenCode target: `installers/opencode.sh install --target <scratch-config>` (sdd requires the `common` domain for `judgment-day`, `native-question-ux`, `grilling`, `code-conventions`, `work-unit-commits`, `tcr`).
3. Open an OpenCode session in the scratch project with `orchestraitor` as the primary agent.
4. Build the fixture kit below per scenario — this repo ships no `.ai/orchestrator/` state; every scenario creates its own.

| Roadmap | `.ai/roadmaps/<goal>.md` | header `Status: active \| Source: deep-planner`, `Outcome:`, slice table `\| # \| Slice \| Scope \| Depends on \| Status \| Bundle \|` with ≥3 slices in mixed states |

Three of these now ship as a real fixture: `scripts/fixtures/sdd-agent-routes/java-orders/` is a Java 17 / Maven project (three classes, three passing tests, `mvn -o test` in about a second) with `state-seeds/{ready-plan,canonical-spec,legacy}/` holding the ready bundle, the canonical-spec-plus-delta set, and the legacy tree. Its `README.md` documents the seed contract, including why seed state is stored un-dotted as `ai/` rather than `.ai/`. Build the remaining fixtures by hand.

Scenario IDs are `SDD-<AREA>-<nn>`. Priorities: **P0** core pipeline, **P1** state and secondary flows, **P2** tooling and periphery.

## Automation

Part of this catalog now runs unattended. Two scripts split along the line that matters — whether a scenario costs money.

| Script | Cost | Wired into `validate-harness.sh` | Covers |
|---|---|---|---|
| `scripts/test-sdd-automode.sh` | free, no LLM, no network | yes (jq-gated) | SDD-AUTO-01, expanded into 14 cases |
| `scripts/test-sdd-flows.sh` | real model calls | no, opt-in via `OPENCODE_BIN` | the smoke set below, driving `orchestraitor` headlessly |

The flow runner uses `opencode run --dir <scratch> --agent orchestraitor --format json --auto`. Every scenario gets a fresh `mktemp -d` copy of the `java-orders` fixture in its own git repo; nothing is written inside this repo or the user's projects, and the user's `~/.config/opencode` is read but never modified. Runs deliberately use the caller's real `HOME`/`XDG` dirs: under a hermetic HOME, session creation hangs because provider credentials never resolve (the same blocker documented in `scripts/test-graphify-init.sh`).

Assertions read three observable sources — the `.ai/orchestrator/` tree on disk, `git log` in the scratch project, and the JSON event stream, where a delegation is a `tool` part named `task` whose `.state.input.subagent_type` names the subagent that ran. That last one is what makes "which subagents were *not* launched" testable.

**Headless gate behavior**, established by `scripts/test-sdd-flows.sh probe`: under `--auto`, a question is neither auto-answered nor hung on. The agent loads `native-question-ux`, renders the question as plain assistant text, and the turn ends. So an automated scenario's prompt must pre-answer the whole kickoff round, or the run stops at the gate leaving partial state on disk. This is why the automated set is entirely `Mode: automatic`, and why every interactive-gate scenario stays manual — the gate is exactly what cannot be observed headlessly.

### What is automated

`SDD-LIGHT-01`, `SDD-FULL-02`, `SDD-ADOPT-01`, `SDD-ARCH-01` and `SDD-JDG-04` run via `scripts/test-sdd-flows.sh smoke`. `SDD-ARCH-02` is asserted as part of the `SDD-ARCH-01` run: the same fixture carries the RENAMED delta and the runner checks the canonical spec for the new name only.

`LITE-01` and `LITE-02` (sdd-lite POC, below) run via `scripts/test-sdd-flows.sh lite`: the runner's `RUN_AGENT` hook drives `orchestralite` instead of the orchestraitor against the same fixture. Both agents must be installed in the caller's real OpenCode config.

### What stays manual

- **Every interactive-mode scenario** (the proposal gate, the specs+design gate, the `commit-per-wave` first-commit confirmation, the `full`-judgment continue/escalate/stop gate). Headless runs end at the question.
- **Multi-session scenarios** — `SDD-RES-01`/`02` resume, `SDD-MIG-01` migration, roadmap hops — need a second session against state the first one left. The runner's one-shot `run` invocation can express this (`--continue`), but the seeds those scenarios need (`resume-full`, `resume-light`, `verify-gap`) are not populated yet.
- **`SDD-VERIFY-02` and `SDD-JDG-03`** are not forceable at all without fault injection: one needs `sdd-verify` to find a real gap, the other needs a judge to return a malformed result. Both depend on a subagent misbehaving on cue, which requires purpose-built stub agents rather than a prompt.

Judgment scenarios carry residual nondeterminism even when automated: `SDD-JDG-04` asserts topology (only `jd-solo` launched, at most one `jd-fix` round, no re-judge) because whether a CRITICAL finding exists at all is up to the judge.

## P0 — Core pipeline

### Full depth

**SDD-FULL-01 — Full interactive happy path** (P0)
- Fixture: clean scratch repo, no `.ai/orchestrator/`.
- Steps: say `"vamos con sdd"` plus a request that spans a new capability across several files. Answer the kickoff: `Depth: full`, `Mode: interactive`, judgment `none`, delivery `none`. Approve each gate.
- Expected: ONE kickoff round (all five questions — Depth, Mode, TDD, Judgment, Delivery — minus anything already stated); phases run explore → proposal → **gate** → specs ∥ design → **gate** → tasks → implement → verify → archive; drafting goes to `sdd-proposal`/`sdd-spec`/`sdd-design`/`sdd-tasks` subagents (the orchestraitor never dumps a draft in chat, only briefs, 1–3 line summaries, and file paths); artifacts land under `.ai/orchestrator/changes/<change>/`.
- Pass: `proposal.md` line 1 is the kickoff line in the recorded shape (`Mode: … | TDD: … | Judgment: … | Depth: full | Delivery: …`); both confirmation gates were asked against the *written* artifact (summary + path); `tasks.md` has the five forecast guard lines and `Files:` per group; after archive the folder sits in `changes/archive/<YYYY-MM-DD>-<change>/` and canonical specs contain the merged deltas.

**SDD-FULL-02 — Full automatic mode** (P0)
- Fixture: same as SDD-FULL-01.
- Steps: same request, kickoff answers `Mode: automatic`, judgment `none`.
- Expected: drafting runs in three blocking waves (`sdd-proposal`; then `sdd-spec` ∥ `sdd-design`; then `sdd-tasks`) with **no** proposal or specs+design gates; the orchestraitor reconciles the four receipts against each other (`first_line`, `capabilities`, `paths`, `forecast_guards`, `open_questions`) and re-delegates to the owning phase agent on contradiction, rereading an artifact only to fix an inconsistency already located; questions only if genuinely blocked, with decisions recorded in `design.md`.
- Pass: zero intermediate confirmation gates between kickoff and the final summary; all four artifacts written; implement/verify ran without pausing for approval.

### Light depth

**SDD-LIGHT-01 — Light happy path with bounded fast-path kickoff** (P0)
- Fixture: clean scratch repo.
- Steps: say `"usa SDD"` with a bounded request (2–3 files, no new capability). Accept the bundle.
- Expected: the orchestraitor assesses `light` and asks ONE accept-or-adjust question proposing `Depth: light | Mode: automatic | TDD: alongside | Judgment: none | Delivery: none` (knobs already stated in the request are substituted, and judgment `light` is recommended instead of `none` if the change touches non-trivial logic); exactly one drafting subagent launches — `sdd-proposal` in light mode, which explores read-only and writes `change.md` via `sdd-draft-light`, returning a receipt with `deltas` and `groups`. The orchestraitor never reads `change.md` to run the gate.
- Pass: single artifact `change.md` (no `proposal.md`/`design.md`/`tasks.md`/delta files) with the kickoff line as line 1 including `Depth: light`, sections `## Why / What`, `## Spec Deltas` (ADDED/MODIFIED/REMOVED semantics), `## Tasks`, under ~800 words; implement/verify/archive then run identically to full depth; verify fix budget is ONE round.

**SDD-LIGHT-02 — Upgrade gate light → full** (P0)
- Fixture: clean scratch repo.
- Steps: start light (as above) with a request deliberately worded to sound bounded but that drafting will reveal as large (>~400 estimated changed lines or a sprawling new capability).
- Expected: `sdd-proposal` writes the light draft anyway and reports the oversized scope in `open_questions` — it never decides the upgrade itself; the orchestraitor reads that field and recommends upgrading to full instead of silently continuing light; on acceptance, the light draft becomes input to the full-depth `sdd-proposal` brief.
- Pass: an explicit upgrade offer was made before implementation; after upgrade, the four full-depth artifacts exist and the flow continues as full.

### Verify reconciliation

**SDD-VERIFY-01 — Valid receipt closes verification** (P0)
- Fixture: any change reaching verify with N scenarios.
- Steps: let the flow run.
- Expected: `sdd-verify` (read-only) returns the terminal line **first** — `VERIFY: ALL PASS — <n>/<n> scenarios.` — then the YAML receipt (`change`, `diff_range`, `scenarios[]`, `gaps`, `blockers`); the orchestraitor reconciles it: identity echoes match the brief, `gaps`/`blockers` empty, scenario ids are exactly the assigned set, every row PASS, `<n>` equals the assigned count, evidence spot-checks clean.
- Pass: verification closed only after reconciliation; `<n>` matches the count assigned in the brief (not the count evaluated).

**SDD-VERIFY-02 — Malformed receipt → re-delegate once → stop and ask** (P0)
- Fixture: hard to force organically; simulate by instructing verify (through the change's scenarios) into an ambiguous scenario set, or review transcript evidence when it happens.
- Steps: observe an incomplete/contradictory receipt (omitted scenario id, count mismatch, ALL PASS alongside a FAIL row, or ALL PASS with non-empty `gaps`).
- Expected: the orchestraitor treats it as *not a verdict*: re-delegates the cold-check ONCE naming the discrepancy; if it persists, stops and asks the user — it never checks boxes or archives on a malformed receipt.
- Pass: exactly one re-delegation before asking; no archive happened on a bad receipt.

**SDD-VERIFY-03 — Fix budget and scoped re-check** (P0)
- Fixture: change whose implementation is seeded with a deliberate scenario-visible defect (e.g. drop one acceptance behavior).
- Steps: run to verify; let it fail; let fix rounds run; at light depth repeat with budget 1.
- Expected: each `gaps` row seeds one `sdd-implement` fix brief; budget is 2 rounds at `full`, 1 at `light`; the re-check after a fix runs scoped to the files the fix touched (the initial cold-check covered every scenario); un-evaluated scenarios appear as FAIL rows with a reason in `gaps` (or a `blockers` entry), never as omissions; if gaps remain after the last round the orchestraitor stops and asks (continue / re-scope / stop).
- Pass: round count never exceeded the depth budget; budget exhaustion produced the three-option question, not a silent archive.

### Implement wave scheduling

**SDD-WAVE-01 — Forecast guard gate** (P0)
- Fixture: full change whose `tasks.md` forecast has `Chained PRs recommended: Yes` or `400-line budget risk: High`.
- Steps: run implement in interactive mode; repeat in automatic mode.
- Expected: interactive — the orchestraitor stops before any wave and confirms the split/chain strategy via `native-question-ux`; automatic — it adopts the forecast's own recommendation, writes it into the `Chain strategy:` guard line in `tasks.md`, reports it in one line, and does not block.
- Pass: interactive asked before wave 1; automatic modified only the `Chain strategy:` line and continued.

**SDD-WAVE-02 — Parallel eligibility** (P0)
- Fixture: `tasks.md` with three groups: two with disjoint `Files:` scopes and no hotspot overlap, one either missing `Files:` or touching a `Shared hotspots:` entry.
- Steps: run implement.
- Expected: only the two eligible waves launch in parallel (single message); the third runs alone; parallel briefs name **scoped** validation only, and the orchestraitor runs the full project test command once itself after the round; it reconciles each receipt from its fields before checking boxes — `tasks_done` covers the wave's tasks, one `assertions` row per task points inside the wave's `Files:` scope, `files_changed` stays in scope — spot-checking a `file:line` only when a row looks wrong, never rereading the wave's files wholesale.
- Pass: the ineligible wave never joined a parallel round; exactly one orchestraitor-run full-suite pass per parallel round.

**SDD-WAVE-03 — `out_of_scope` drops parallelism** (P0)
- Fixture: wave scopes drawn so one wave will necessarily touch a file outside its declared scope.
- Steps: run implement.
- Expected: the receipt's non-empty `out_of_scope` drops the parallel assumption; the next round runs sequentially unless scopes are re-planned.
- Pass: the round after the violating receipt was sequential.

### Judgment

**SDD-JDG-01 — Full dual protocol: blind judges and synthesis** (P0)
- Fixture: completed change with 2–3 seeded defects spanning categories (one correctness, one security); kickoff `Judgment: full`; `.ai/atl/skill-registry.md` present.
- Steps: let judgment run.
- Expected: `jd-judge-a` and `jd-judge-b` launch in parallel, blind (no prompt mentions the other judge or its findings); registry-distilled `## Project Standards (auto-resolved)` block (3–5 skills max) injected identically into both judge prompts and the fix prompt; synthesis by the orchestraitor only: Confirmed (both), Emphasis-confirmed (one judge inside its zone — A = correctness+edge-case, B = security+performance — at CRITICAL/WARNING; `standards` findings never emphasis-confirm), Suspect (triage only, never auto-fixed), Contradiction (manual decision); `Judgment: full` pre-answers the verdict gate, so confirmed + emphasis-confirmed go straight to `jd-fix`.
- Pass: ledger in `.ai/orchestrator/changes/<change>/judgment.md` with stable `JA-nnn`/`JB-nnn` ids; only confirmed/emphasis-confirmed ids reached `jd-fix` (`FIX: <n> fixed, <m> open.`); suspects stayed in the ledger for human triage; after the last fix round `sdd-verify` re-ran scoped to the files `jd-fix` touched before archive.

**SDD-JDG-02 — Re-judge loop, gates, and escalation** (P0)
- Fixture: as SDD-JDG-01, with at least one defect `jd-fix` is told about but that has a second layer (so a re-judge keeps it `open`).
- Steps: run `Judgment: full`; at each loop gate choose *Continue*.
- Expected: every re-judge and any fix after the first requires user confirmation (continue / escalate / stop) via `native-question-ux` — delegates never ask; the re-judge brief carries only the ids sent to `jd-fix`; in re-judge rounds the CLEAN token is invalid — a valid result is exactly one `verdicts` row per briefed id; reconciliation: both `fixed` → `verified`, both `refuted` → `refuted`, split → `fixed` + contradiction note; after 2 fix iterations the protocol ends in `JUDGMENT: ESCALATED ⚠️` with full history.
- Pass: max 2 fix rounds; escalation token emitted; ledger ids never renumbered across rounds.

**SDD-JDG-03 — Invalid judge result → retry once → INVALID ROUND** (P0)
- Fixture: same target; this failure is environmental (empty/truncated judge return, or a notes-only response with no CLEAN token) — test opportunistically or by constraining the target to something un-reviewable for one judge.
- Expected: a malformed result is never treated as CLEAN; only the failing judge is relaunched once, fresh and blind; a second failure yields `JUDGMENT: INVALID ROUND ⚠️`, preserving the valid judge's findings in the ledger as unsynthesized; never synthesize from one judge, never report clean.
- Pass: retry targeted a single judge; no synthesis happened from one judge's findings.

**SDD-JDG-04 — Light judgment (`Judgment: light` / `/judgment light`)** (P0)
- Fixture: completed bounded change with one seeded CRITICAL-class defect and one cosmetic issue; kickoff `Judgment: light`. Also run standalone `/judgment light <target>`.
- Expected: only `jd-solo` launches (ids `JS-nnn`, balanced all-category sweep, no emphasis zones, no Pattern 2 synthesis); CRITICALs go straight to `jd-fix` without asking — max ONE fix round, **never** a re-judge (`jd-solo` given a ledger + fix diff must refuse and state light mode does not re-judge); WARNING/SUGGESTION only reported; in-flow, `sdd-verify` re-runs scoped to `jd-fix`'s files before archive; verdict tokens from the LIGHT family (`JUDGMENT: LIGHT APPROVED ✅` / `LIGHT VERDICT 📋` / `LIGHT FIXED (unverified) 🔧`); multiple CRITICALs → recommends re-running the full dual protocol instead of looping light rounds.
- Pass: `jd-judge-a`/`jd-judge-b` never launched; exactly ≤1 fix round; no re-judge occurred.

**SDD-RES-02 — Interruption after implement** (P1 — **negative, expected FAIL today**)
- Known defect: no durable checkpoint exists for the post-implementation phases (verify / judgment / merge / archive).
- Fixture: change where all tasks are checked but verify/judgment/archive did not run; resume in a fresh session.
- Expected (today): the orchestraitor cannot reliably tell which post-implement phase is pending — it may repeat verify, skip judgment, or strand the archive.
- Pass criterion for the *test*: document what resume actually does from that state.

**SDD-ROAD-01 — Roadmap slice hop at archive** (P1)
